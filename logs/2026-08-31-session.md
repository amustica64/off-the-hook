## Task 2, enc_key. Fixed, and the test can now fail

Migration `0002_enc_key_vault.sql`. `enc_key()` reads the Vault secret
`app_enc_key` from `vault.decrypted_secrets` first, per Doc 13 §7 ("the
encryption key move[s] into the real Supabase Vault, not a GUC"), and falls back
to the GUC so local development and the proof still run.

It stays SECURITY INVOKER deliberately. Called from inside the definer RPCs it
runs with their privileges and can read the Vault; called directly by `anon` or
`authenticated` it has no privilege on the vault schema, `to_regclass` returns
null, and there is no path to the production key. Execute is revoked from
public, anon and authenticated as well. Making it SECURITY DEFINER would have
handed any caller the key.

**The GUC is no longer per connection.** `db/dev-key.sql`, wired as `pnpm
db:key`, sets it as a database default that every new connection inherits. A
per-connection `SET` is fragile under a transaction-mode pooler, which hands a
pooled backend to the next caller, and that fragility is the shape of the
original bug.

### The test no longer proves its own harness

This was the important half. `rls-proof.sql` used to call
`set_config('app.enc_key', 'dev-only-key', false)` two lines above the RPC it
was testing, so it arranged a condition the application never arranged. That is
why the defect survived eleven sessions.

It now provisions nothing. A new section 3b asserts `create_referral` fails with
`encryption key not configured` when no key is reachable, and sections 4 and 10
rely on the environment exactly as the application does.

Proved in both directions:

```
proof with no key provisioned   FAILED: encryption key not configured
pnpm db:key, then the proof     ALL RLS PROOFS PASSED
```

The first line is the one that matters. Before today the proof passed in that
state.

The guard also restores the key it borrows. First attempt leaked, because the
whole file runs inside one implicit transaction under the simple query protocol,
so a transaction-scoped `set_config` blanked the key for every later section.
The proof now also clears its own referral fixtures by referrer address, so a
row written under a different key cannot fail section 10 and read as a code
defect. That is exactly what happened on the first run after the fix.

## A process finding worth keeping

Two tests failed mid-session in a way that looked like a font regression and a
missing anchor. Neither was real. A `next start` from an earlier background task
still held port 3100, so every new `next start` failed silently on EADDRINUSE
and the suite kept hitting a zombie server running a build that no longer
existed on disk. The tell was that the served CSS filename did not match the one
in `.next/static/css`.

Worth a habit: check the served asset hash against disk before believing a
surprising test failure, and kill listeners on the port rather than assuming a
new server took it.
